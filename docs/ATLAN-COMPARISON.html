PBIP Lineage Explorer and Atlan: overlap, gaps, and how they fit together

How the in-house PBIP Lineage Explorer compares with Atlan's Microsoft Power BI connector, where each one is the better tool, and practical ways to use them together.

Based on Atlan's public connector docs, October 2026 App facts verified against the source code

1. The short version

The two tools work at different stages of a report's life.

Atlan

Catalogues what is already published, tenant-wide, alongside your warehouses and pipelines.

  • Broad: every crawled workspace and report
  • Shared, governed, scheduled
  • Lineage reaches the report page

PBIP Lineage Explorer

Reads the source files (PBIP) on someone's machine, before or after publishing.

  • Deep: every measure, visual, filter, and role in the files you load
  • Personal, local, instant
  • Lineage reaches the individual visual

They overlap less than you might expect, and each covers the other's main blind spot. Atlan cannot see work that has not been published yet or the fine structure inside a model. The app cannot see reports that nobody loaded, or whether anyone actually views them.

4. What Atlan already does

  • Asset inventory. Workspaces, apps, dashboards, tiles, reports, pages, semantic models, tables, columns, measures, dataflows, and data sources.
  • DAX text. Stored on each measure as powerBIMeasureExpression, but only when the "Enhance admin APIs responses with DAX and mashup expressions" tenant setting is on.
  • Upstream lineage to the warehouse. Table and column level to Snowflake, Databricks, BigQuery, SQL Server, Synapse, Oracle, Redshift, and others. It follows Power Query renames such as Table.RenameColumns, the same idea as the app's rename tracing.
  • Column and measure → page lineage. Now built into the base connector (the separate app that used to do this is deprecated). It needs Contributor-or-higher workspace access and the scanner-only toggle switched off.
  • Usage and popularity. The Power BI miner counts views and distinct users for reports and dashboards.
  • Governance. Owners, glossary terms, tags, certification, search, and discussions on every asset.

5. Where the app goes further

  1. Works before publishing. It reads the files a developer is editing, so impact can be checked during a pull request or on a feature branch. Atlan only sees a change after it is published and the next crawl runs.
  2. Visual-level detail. Atlan's lineage stops at the page, and visuals are not catalogued as assets. The app traces to each visual and can show where it sits on the page.
  3. Measure-to-measure dependencies. The Measure Map, Dependents grid, and DAX chain show which measures are built on which. Atlan's docs store each measure's DAX text but do not describe lineage between measures.
  4. Graded orphans. Four statuses (in use, filter/RLS, no visual, true orphan) plus a separate unused-columns list. Atlan's docs do not describe orphan detection.
  5. Model features Atlan's docs do not mention. Field parameters, calculation groups, row-level-security roles, whether a filter is actually applied, bookmarks, and hidden visuals.
  6. Commit-by-commit change history. Each measure change comes with the visuals it affects. Atlan shows the current state, not a diff.
  7. No tenant permissions. No service principal, admin API access, or tenant-setting changes. A review committee will notice this: Atlan's connector needs all three.

6. Where Atlan is stronger

  1. It sees everything that is published. The app only knows about reports someone saved as PBIP and loaded. This is its biggest blind spot and the reason its orphan lists need a human check.
  2. Usage data. Atlan can tell you a report has had no views in months. The app can tell you a measure is wired to a visual, but not whether anyone looks at it.
  3. End-to-end lineage. Atlan connects Power BI back through the warehouse and transformation pipelines. The app stops at the Power Query source table and column.
  4. Shared, governed, always running. Owners, glossary, searchable history, and scheduled crawls, available to everyone. The app is a personal analysis tool.

Use each at its stage

Developers use the app while building and reviewing changes. Atlan stays the production catalogue and governance record. There is no conflict, because the app never writes to anything.

Works today
2

Make better cleanup decisions

Combine the two signals. A True Orphan in the app, inside a report Atlan shows as unviewed, is a strong deletion candidate. A measure the app calls "in use" that sits only on a report nobody opens is cleanup worth raising with the owner. Neither tool can make that call alone.

Works today
3

Close the "only what you loaded" gap

Atlan's lineage lists every published report built on a semantic model. Use that list to collect the right PBIP folders before running a cross-report impact check in the app, so its orphan and impact results cover every consumer.

Works today
4

Push the app's findings into Atlan

Atlan's Python SDK (pyatlan) can create custom lineage and attach metadata to existing assets. The app's engine is a standalone JavaScript module, so a script could export measure-to-measure dependencies or orphan status and write them onto Atlan's PowerBIMeasure assets. That would fill Atlan's measure-dependency gap for everyone who uses the catalogue. The hard part is matching names: PBIP files do not contain Power BI Service workspace or dataset IDs, so you would match on model, table, and measure name.

Needs development
5

Analyse published reports without PBIP saves

Atlan has an optional "Fetch Extracts for Context Agents" setting that downloads PBIR and TMDL definitions of published reports into object storage. If those extracts match the PBIP folder layout, the app's engine could read them, giving it tenant-wide coverage from Atlan's existing crawl. The format has not been verified; test with one report before planning around it.

Worth investigating

8. Caveats

Atlan's docs contradict themselves on measure lineageOne FAQ says "Atlan currently does not support lineage for Microsoft Power BI measures", while the crawl reference and the lineage how-to say measure → page lineage is supported. The FAQ looks out of date, but confirm with your Atlan admin or account team.

  • "Not documented" is not "not available". Points in this page about Atlan lacking something mean its public documentation does not mention it. Atlan ships frequently, so check measure-to-measure lineage, visual-level lineage, and field-parameter handling against your own tenant before presenting them as gaps.
  • Your tenant may not have the full feature set. Page-level lineage depends on how your Atlan connection is configured: the scanner toggle, workspace roles, and the DAX tenant setting. In scanner-only mode Atlan extracts no report pages, and measure-level lineage is degraded.
  • The app's results depend on what is loaded. Its orphan and impact lists cover only the PBIP folders opened in a session. Treat them as findings to confirm, not actions to take automatically.
