Proposal · future additions

An AI skill set for the PBIP Lineage Explorer

A set of AI assistant skills that read the same PBIP folders as the app, explain what you are looking at, walk you through orphan cleanup one decision at a time, and remind you which measures and visuals depend on anything you ask the AI to change.

Status: proposal, not built Target: Claude Code skills, stored in the repo Builds on the existing lineage engine

1. The idea

The Lineage Explorer is good at showing lineage. People still have to read it, decide what it means, and then go and make the change in Power BI by hand. An AI assistant can close that gap, if it works from the same facts the app does.

The proposal is a small set of skills: packaged instructions an AI assistant (Claude Code) loads when a user asks for a particular kind of help. Each skill would:

  • read the PBIP folder using the same engine as the app, so its answers about dependencies, visuals, and orphan status match what the app shows;
  • explain findings in plain language and answer follow-up questions;
  • for skills that change files, show the impact first, ask for confirmation, make the edit, then re-run the analysis to prove nothing unexpected broke.

The key design choiceThe AI never works out lineage on its own by reading DAX and guessing. It asks the lineage engine, which already has 133 tests behind it. The AI's job is to explain, ask the right questions, and carry out edits carefully. That keeps the answers consistent with the app and much harder to get wrong.

2. How it would work

Three building blocks. Only the first needs new engineering; the other two are mostly writing.

Foundation · new

Lineage command-line tool

A small Node script that runs the existing engine (packages/core) against a folder and prints the answer as JSON. The VS Code extension already runs the engine in Node, so this is a thin wrapper, not new logic.

The skills

Skill pack in the repo

One folder per skill under .claude/skills/, each with a SKILL.md describing when it applies, which commands to run, what to ask the user, and what it must never do. Versioned with the app.

App hand-off · new

"Copy for AI" button

The AI cannot see the browser tab. A button in the app would copy the current selection (measure or visual, its status, dependents, and visuals) as a short text block to paste into the AI chat, so "explain what I'm looking at" just works.

3. Ground rules every skill follows

These go into every skill's instructions. They are what make AI edits to a Power BI model safe enough to use.

Facts come from the engine

Dependencies, visuals, and orphan status are always looked up with the CLI, never inferred from reading DAX. If the engine and the AI disagree, the engine wins.

Impact before any edit

Before changing, renaming, or deleting anything, list what depends on it: dependent measures, visuals with report and page, active filters, RLS rules. Then ask.

One confirmation per deletion

Deletions are never bulk-approved by default. The user chooses which statuses are in scope and confirms each item, or explicitly approves a listed batch.

Work on a branch

Edits happen on a new git branch, so every change can be reviewed and undone. If the folder is not a git repo, the skill makes a backup copy first.

Prove it afterwards

After editing, re-run the analysis and show a before/after: which statuses changed, and that no visual lost a field it still needs.

Close Power BI Desktop

Desktop does not reload PBIP files that change on disk and can overwrite edits when it saves. Skills that edit files check with the user that the project is closed first.

Say what was not loaded

Every answer about usage repeats the app's limit: only the loaded folders were checked. Reports elsewhere, Excel connections, and paginated reports are invisible.

Stay in the folder

Skills read and write only inside the chosen PBIP folder. They never publish to the Power BI Service or touch a workspace.

4. The three core skills

These are the three you asked for. They share the CLI and the ground rules above.

Lineage Guide

pbip-lineage-guide

Explains what you are looking at in the app, and answers any question about how measures, visuals, and sources connect.

You might say
"Explain this measure." · "Why is YoY Growth flagged as no visual?" · "Which visuals use Total Sales, and on which pages?" · "What source column does Sales Amount come from?"
What it does
  • Reads a pasted "Copy for AI" block, or looks the item up by name.
  • Explains the DAX in plain words, then lists what it depends on and what depends on it.
  • Explains its usage status using the app's four definitions, and why it landed there.
  • Suggests where to look next ("open the Measure Map on Total Sales to see all 4 visuals").
Never
Edits files. This skill is read-only.
Labels
Read-onlySize: small

Orphan Cleanup

pbip-orphan-cleanup

Walks through unused measures and columns, lets you choose which orphan definitions to act on, and removes only what you approve.

You might say
"Help me clean up unused measures." · "Delete the true orphans." · "What's safe to remove from this model?"
What it does
  1. Loads the whole workspace folder if there is one, and reminds you that unloaded reports are not checked.
  2. Shows counts for each status with the app's definitions: True orphans (safest), Visual orphans (investigate), Filter/RLS (usually keep), and unused columns.
  3. Asks which statuses you want in scope. By default it offers only True orphans and warns before including Filter/RLS, since those control what users see.
  4. For Visual orphans, shows the chain (A is used only by B, which nothing uses) and offers to remove the chain together.
  5. Lists each candidate with its DAX and table, and asks you to keep, delete, or skip.
  6. Removes approved measures from the TMDL files on a new branch, re-runs the analysis, and shows the new counts.
  7. Writes a short cleanup log you can attach to the pull request.
Never
Deletes anything you have not explicitly approved, deletes a Filter/RLS measure without a second warning, or touches report visuals.
Labels
Edits model filesSize: medium

Safe Measure Change

pbip-safe-change

Any time you ask the AI to change a measure, it first reminds you of everything that depends on it, then makes the change and checks the result.

You might say
"Change Total Sales to exclude returns." · "Rewrite Margin % to use DIVIDE." · "Update YoY Growth to fiscal years."
What it does
  1. Looks up the measure and shows a short impact card: dependent measures (direct and indirect), visuals by report and page, active filters, RLS rules.
  2. Flags high-risk cases: many dependents, use in RLS, use in a field parameter or calculation group.
  3. Proposes the new DAX, shows the old and new side by side, and asks for approval.
  4. Applies the edit on a branch, re-runs the analysis, and confirms the dependency picture is unchanged (or explains what changed, for example a new column reference).
  5. Lists which visuals to spot-check in Power BI Desktop before publishing.
Never
Edits a measure without showing the impact card first, or changes other measures as a side effect without asking.
Labels
Edits model filesSize: medium

5. More skill ideas

Each of these pairs naturally with something the app already computes.

Rename & Refactor

pbip-rename

Renames a measure or column everywhere it is used, so no visual breaks.

Why it helps
A rename in one place silently breaks every DAX reference to the old name and every visual, filter, and bookmark that binds it. The app already knows all of those locations.
What it does
Updates the definition, every DAX reference, visual field bindings, filter entries, and field parameter lists across all loaded reports. Re-runs the analysis to confirm no orphaned or missing references.
Labels
Edits model and report filesSize: large

Visual Naming

pbip-visual-names

Finds data visuals still carrying a default name, such as "Table", "Matrix", or no title at all, and gives each one a name that describes what it shows.

Why it helps
When a visual has no title, the app can only label it by type: Table (3 measures) in the sidebar and just tableEx or pivotTable in the lineage tree. On a page with four untitled tables, the Measure Map and impact lists show four identical boxes. Descriptive names make every lineage view, export, and change report readable.
What counts as default
  • No title text set.
  • A title that is just a type or placeholder: "Table", "Matrix", "Chart", "Card", "Visual 1", "Copy of Table".
  • Groups still named "Group 1", "Group 2" (optional).
  • Only visuals that are bound to data. Text boxes, shapes, images, and buttons without fields are skipped.
How names are built
  • From the visual's fields by role, which the engine already records: main measures (Values, Y-axis) first, then the grouping columns (Rows, Category, X-axis, Legend). For example, a matrix with Total Sales and Margin % by Region and Month becomes Total Sales & Margin % by Region, Month.
  • Simple patterns per type: a card takes its measure name, a slicer becomes Slicer: Region, and a wide detail table becomes Customer detail (8 columns).
  • Field parameter display names are used when present.
  • Names are kept short (about 40 characters), made unique on each page, and follow the team's naming convention if one exists.
Where the name goes
ModeWhat changesReport readers see
Hidden title (default)Writes the title text into visual.json with the title's show switch left offNo change. The app and other tools that read titles pick up the new name.
Visible titleWrites the title text and turns the title onA new title above the visual. Needs the report owner's sign-off, since it changes the design.
App-only namesWrites a small names file the app reads alongside the PBIP; no PBIP file changesNo change. Requires a small app feature to read the file.

In hidden-title mode the edit to each visual.json looks like this:

"visualContainerObjects": {
  "title": [{ "properties": {
    "show": { "expr": { "Literal": { "Value": "false" } } },
    "text": { "expr": { "Literal": { "Value": "'Total Sales by Region'" } } }
  } }]
}
What it does
  1. Scans every loaded report and lists default-named data visuals in a table: report, page, type, current label, fields by role, and the proposed name.
  2. Lets you accept, edit, or skip each name, or accept a page or a whole report at once.
  3. Asks which mode to use, defaulting to hidden titles.
  4. Confirms the project is closed in Power BI Desktop, writes the titles on a new branch, then re-runs the analysis. It shows how many visuals still use a default name, and confirms every visual kept exactly the same fields.
Never
Overwrites a title someone wrote, changes a visual's fields, formatting, or position, or turns on a visible title without asking.
Pairs with
A cheap app improvement worth doing regardless: make the fallback label for untitled visuals use the main fields (Table: Total Sales, Region) instead of the type alone.
Labels
Edits report files (titles only)Size: medium

Change Review

pbip-change-review

Summarises a branch or pull request in plain language, with the visuals each change affects.

Why it helps
Reviewers currently read raw JSON diffs. The engine's change detection already classifies 29 kinds of change.
What it does
Runs diff against the target branch, groups changes by risk (measure logic, relationships, Power Query sources first), lists affected visuals by report and page, and drafts a review comment. Calls out relationship and source changes for manual checking, since automatic visual impact is only worked out for measures.
Labels
Read-onlySize: small

Source Change Impact

pbip-source-impact

For data engineers: "this warehouse column is being renamed or dropped; what breaks?"

Why it helps
The Source Map already links every Power BI column to its original database table and column, including Power Query renames.
What it does
Finds the Power BI columns fed by a source column or table, then every measure and visual downstream of them, across all loaded reports. Produces a list the engineer can send to report owners.
Labels
Read-onlySize: small

Measure Documentation

pbip-document

Writes plain-language descriptions for measures and produces a data dictionary.

Why it helps
Descriptions show as tooltips in Power BI and in catalogues like Atlan, but most models have few. The AI can draft them from the DAX plus the lineage context.
What it does
Drafts a description for each undocumented measure (what it calculates, key filters, source tables), lets the user approve or edit each one, writes them into the TMDL files, and can export a data dictionary page.
Labels
Edits model files (descriptions only)Size: medium

Model Health Report

pbip-health-report

Produces a short, shareable health summary for a model or workspace.

What it does
Turns the Model Health numbers into a one-page report: orphan counts by status and their trend since the last report, most-depended-on measures (the riskiest to change), hidden fields still in use, and recent changes. Useful before a release or for a quarterly review.
Labels
Read-onlySize: small

Duplicates & Conventions

pbip-conventions

Finds near-duplicate measures and naming or folder inconsistencies.

What it does
Spots measures with identical or nearly identical DAX (three versions of "Total Sales" in different tables), checks names against a team convention, and suggests consolidating, with the impact of each consolidation shown first. Hands off to Rename & Refactor to carry it out.
Labels
Read-only (hands off edits)Size: medium

Security Review

pbip-rls-review

Explains the model's row-level security in plain language.

What it does
Lists each RLS role, the tables it filters, and the measures and columns its rules depend on. Warns when a pending change touches anything an RLS rule uses, which is the kind of change that can quietly widen what users can see.
Labels
Read-onlySize: small

Report Onboarding

pbip-onboarding

Gives a new analyst a guided tour of an unfamiliar report.

What it does
Walks page by page: what each page shows, the handful of key measures behind it, where the data comes from, and which measures everything else is built on. Answers questions as it goes, using the Lineage Guide's lookups.
Labels
Read-onlySize: small

Atlan Sync

pbip-atlan-sync

Pushes the app's measure-to-measure dependencies and orphan status into Atlan.

Why it helps
Atlan's documentation does not describe measure-to-measure lineage or orphan detection. This fills that gap for everyone who uses the catalogue (see the Atlan comparison guide).
What it does
Matches PBIP measures to Atlan's PowerBIMeasure assets by model, table, and measure name, shows the proposed updates for approval, and writes them through Atlan's Python SDK. Can also pull Atlan's report view counts back in to sharpen cleanup decisions.

Writes to AtlanNeeds Atlan API accessSize: large

6. Example conversations

Illustrations of the intended behaviour. The counts, names, and dependencies come from running the current engine on the app's bundled sample project; the wording is illustrative, since no skill exists yet.

Orphan Cleanup
User

Help me clean up unused measures in this model.

Assistant

I checked the loaded project (1 report, 7 measures):

  • True orphans: 3. Product Count, Selected Metric, Unused Metric. Nothing references them.
  • Visual orphans: 1. Total Quantity. Other things reference it, but none of them reach a visual.
  • Filter/RLS only: 0.
  • There are also 6 unused columns, listed separately.

I only checked this folder. If other reports use this model, load their folders before deleting anything. Which statuses do you want to review?

User

Just the true orphans for now.

Assistant

Three to go through, one at a time.

1. Unused Metric (Sales): COUNTROWS(Sales) * 0. It always returns 0. Delete, keep, or skip?

User

Delete.

Assistant

2. Product Count (Products): DISTINCTCOUNT(Products[ProductID]). Looks like a real metric that was never placed on a page. Delete, keep, or skip?

User

Delete.

Assistant

3. Selected Metric (Sales Metrics) is the SWITCH measure for the Sales Metrics field parameter. No visual uses it. Note: it is one of the two things referencing Total Quantity. The other is the parameter's own Metric column, so deleting it would not change Total Quantity's status. Delete, keep, or skip?

User

Keep that one, someone may be building a page with it.

Assistant

Kept. Before I edit: is the project closed in Power BI Desktop? Desktop can overwrite file edits when it saves.

User

It's closed.

Assistant

Done on branch cleanup/orphans: removed Unused Metric from Sales.tmdl and Product Count from Products.tmdl. I re-ran the analysis: 1 true orphan remains (Selected Metric, kept on purpose), Total Quantity is still a visual orphan, and no visual lost a field. A cleanup log is ready for the pull request.

Safe Measure Change
User

Change Total Sales to exclude zero amounts.

Assistant

Before I change it, here is what depends on Total Sales:

  • 3 dependents: YoY Growth (uses it twice), Selected Metric, and the Sales Metrics field parameter's Metric column, which lists it as an option.
  • 4 visuals: Sales by Category and Sales Detail on Sales Overview; Sales by Region and YoY Growth Trend on Customer Analysis.
  • No active filters or RLS rules use it.

Every number on those 4 visuals will change. Current: SUM(Sales[Amount]). Proposed: CALCULATE(SUM(Sales[Amount]), Sales[Amount] <> 0). Apply it?

Lineage Guide, with "Copy for AI"
User

[pastes the app's copied context for YoY Growth] Why does this list only one upstream measure? The DAX mentions Total Sales twice.

8. Suggested roadmap

Read-only skills first. They are low risk, prove the approach, and build trust before anything edits a model.

Phase 0foundation

Lineage CLI and "Copy for AI"

Wrap the engine in a command-line tool with JSON output, add tests that its answers match the app's, and add the copy button to the app. Nothing else works without this.

Phase 1read-only

Lineage Guide, Change Review, Source Change Impact, Model Health Report

Useful on day one, cannot damage anything, and exercise every CLI command.

Phase 2assisted edits

Safe Measure Change, Orphan Cleanup, Visual Naming, Measure Documentation

Introduce edits with the full ground rules: impact first, per-item confirmation, branch, re-run, before/after. Visual Naming is a good first edit skill: in hidden-title mode it changes nothing a report reader sees, and it makes every later lineage view easier to read.

Phase 3wider reach

Rename & Refactor, Duplicates & Conventions, Security Review, Onboarding, Atlan Sync

Cross-file edits and external integrations, once the edit pattern has a track record.

9. Risks and open questions

This changes the privacy storyToday the app's strongest selling point is that nothing leaves the user's machine. An AI assistant sends what it reads (DAX, table and column names, connection details, RLS rules) to the AI provider to generate its answers. That needs to be approved under the organisation's AI usage policy and covered by an enterprise agreement before any of these skills are used on real models. The app itself stays 100% local either way.

RiskMitigation
The AI writes incorrect DAXShow old and new side by side, require approval, re-run the lineage check, and list visuals to test in Desktop. The skill never publishes.
Deleting something used outside the loaded filesEvery cleanup repeats the "only what's loaded" limit, defaults to True orphans only, and can cross-check report usage in Atlan where available.
Power BI Desktop overwrites editsGround rule: confirm the project is closed before editing.
PBIR or TMDL format changes in a future Power BI releaseEdits go through tested helpers rather than free-form text replacement; the CLI's test suite catches format drift.
Users over-trust the assistantBranches and pull requests keep a human review step; skills explain their reasoning and cite the engine's output.

Questions to settle before building

  • Which AI assistant is approved for use with model metadata, and does its agreement cover it?
  • Should edit skills be available to everyone, or only to report developers?
  • Is there a team naming convention to encode in the Duplicates & Conventions skill?
  • Is Atlan API access available for a sync, and who would own that integration?
