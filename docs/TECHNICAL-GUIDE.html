PBIP Lineage Explorer: what it is, how it works, and what to know before adopting it

A browser tool that reads a Power BI project folder and answers "where does this number come from, and what breaks if I change it?" This guide is written so you can explain the tool to analysts, developers, and a review committee without reading the source code.

Fork maintained in-house (Abearstudios) Upstream: JonathanJihwanKim/pbip-lineage-explorer MIT License 100% in the browser, no server ~14,500 lines of JavaScript 133 automated tests

1. What it does, in plain terms

Power BI Desktop can save a report as a PBIP project: a folder of plain-text files instead of one binary .pbix. Inside that folder, the semantic model (tables, columns, DAX measures, data source connections, security roles) and the report (pages, visuals, filters) are each described in text files. The Lineage Explorer reads those files and builds a map of how everything connects.

With that map it can answer five questions in one click:

  • Where does this visual get its data? Visual → DAX measure → sub-measures → table columns → Power Query step → source database table and column, including columns that were renamed along the way.
  • What breaks if I change this measure? Every measure that depends on it and every visual, page, and report that displays it.
  • What is unused? Measures and columns that nothing on any report actually uses, graded by how disconnected they are (see section 7).
  • How do all the measures relate? A spreadsheet-style grid of every measure with its dependency counts, and a map centred on any one measure.
  • What changed recently? If the folder is a git repository, it reads the commit history and lists what changed, commit by commit, and which visuals that affects.
1. You pick a folderChrome or Edge asks you to choose the PBIP folder (or a folder of several PBIP reports). The browser reads the text files locally.
→
2. It parses the filesTMDL files become tables, columns, measures, and security roles. JSON files become pages, visuals, and filters. DAX text is scanned for references.
→
3. It builds a graphEvery object is a node; every "uses" relationship is an edge. This is the lineage graph.
→
4. You exploreClick a measure or visual, and the tool walks the graph and draws the result.

The one-sentence version for a non-technical audienceIt is a read-only "X-ray" of a Power BI report that shows which calculations feed which charts and which database columns feed those calculations, so changes can be made safely.

2. The app, section by section

Everything lives on one screen. Here is what each area is for.

Launcher

start.bat (Windows) or start.command (macOS) checks for Node.js, installs dependencies the first time, starts a local web server on the user's own machine, and opens the browser. Nothing runs anywhere else.

Welcome screen

Open Project Folder picks a PBIP folder or a folder containing several reports; Try Sample Project loads a small bundled example. Folders can also be dragged in.

Toolbar

Project stats (tables, measures, visuals, orphans) plus buttons for Measure Map, Health, Source Map, Export All, and keyboard help.

Sidebar: Measures tab

Every DAX measure, searchable, grouped by table. Each carries a status badge (orphan, no visual, filter/RLS, or none). The "True orphans only" filter shows measures that nothing references at all.

Sidebar: Visuals tab

Every visual grouped by page, and by report when several reports are loaded. Each page has a Layout button that draws where the visuals sit on the canvas.

Sidebar: Dependents tab

A flat, sortable grid with one row per measure: how many measures it depends on, how many depend on it, columns, visuals, pages, reports, active filters, its status, and its formula. Exports to CSV.

Lineage view (main panel)

After you click a measure or visual: an interactive tree (Visual → Measure → Table/Column → Power Query → Source) and detail sections: a four-column Dependencies strip (visuals, downstream measures, upstream measures, upstream columns), the DAX dependency chain with highlighted code, a source-column table with rename history, and recent changes.

Impact panel

Slide-over listing everything upstream (what this depends on) and downstream (what depends on this). Exportable as Markdown.

Measure Map

One measure at the centre of the diagram. Left: measures it depends on. Right: measures built on it, then every visual it reaches, labelled by report and page. A searchable list of all measures sits beside it; clicking any measure re-centres the map.

Source Map

A flat, searchable table: every Power BI column mapped to its original database table and column, with server and database. Exports to CSV. Aimed at data engineers.

Model Health

Dashboard of counts, data sources, relationships, field parameters, calculation groups, and four orphan lists: True, Visual, Filter/RLS, and unused columns.

Change History

If the folder is a git repo, the tool reads the local commit history and reports what changed (measures, visuals, filters, pages, relationships, sources) and which visuals are affected.

6. Security and privacy

Short answerNothing leaves the user's machine. The tool is a static web page served from the user's own PC (or an internal host). It reads the files you explicitly pick, in memory, in your browser tab, and makes no network calls with that data. There is no server-side component, no account, no database, and no telemetry.

What was verified in the code

QuestionFinding
Does it upload the project files?No. The only outbound request in the source is a fetch() of the bundled sample project from the app's own origin (used by the "Try Sample" button). No request carries user data.
Does it phone home or collect analytics?No. There are no analytics scripts, no tracking pixels, and no third-party scripts in index.html. The only outbound link is a credit link to the original project's GitHub page on the welcome screen, which opens only if a user clicks it. After a few lineage traces the app shows a small in-page note ("You saved about N minutes"); that is local text with no link and no network activity.
How does it read files?Through the browser's File System Access API in read-only mode (showDirectoryPicker({ mode: 'read' })). The user must choose the folder each time; the page cannot browse the disk on its own. It never writes to the folder.
Does it modify Power BI files?No. It is read-only by design. The only files it creates are exports the user explicitly requests (CSV, SVG, PNG, Markdown), which download through the normal browser download prompt.
What does the git feature touch?It reads the local .git folder (objects and refs) with isomorphic-git to diff commits. It does not fetch, push, or contact a remote, and needs no credentials.
What does it do with security roles?It reads RLS role definitions (TMDL role files) to see which measures and columns the filter expressions reference. It only uses this to grade usage; it does not evaluate or enforce the rules and does not display row data (there is no row data in a PBIP folder).
What is stored in the browser?Only UI preferences in localStorage/sessionStorage: a tree-view toggle, a "show hidden visuals" checkbox, and whether the one-time note was shown. No project content is persisted. Closing the tab discards the parsed data.
Does it need admin rights or installs?No admin rights. The launcher needs Node.js installed once (a standard developer runtime); end users of a hosted copy need only a browser.

What a reviewer should still consider

  • The metadata itself is sensitive. PBIP files contain DAX formulas, table and column names, RLS rule expressions, and Power Query connection strings (server names, database names, sometimes schemas). The tool shows these on screen and includes them in exports. This is the same information a developer already sees in Power BI Desktop, but exported CSV/PNG files should be handled like any internal design document.
  • Host it internally if hosting at all. The upstream project runs a public demo on GitHub Pages. Because the app is client-side, even that copy would not upload files, but running the launcher locally or hosting the built dist/ on internal infrastructure removes any doubt and lets you control the version.
  • Secure context requirement. The File System Access API only works over HTTPS or localhost. Opening the HTML directly from a file share (file://) will not work. The launcher uses localhost, which satisfies this.
  • Supply chain. Two runtime dependencies, both widely used and version-pinned in the lock file. Run npm audit as part of any build pipeline and build on your own machines rather than trusting a prebuilt bundle.
  • Browser policy. Some enterprise browser policies disable the File System Access API. If so, the fallback folder picker still works, but drag-and-drop and the git feature may not.
  • Parsing untrusted input. The tool parses JSON and TMDL text with regular expressions and JSON.parse; it never evaluates DAX, M, or role expressions as code. A malformed file produces a console warning and is skipped, not executed.

7. Orphans, defined

"Orphan" is used loosely in Power BI circles to mean "a measure nobody uses". The app is more precise than that: it grades every measure into one of four usage statuses, and keeps unused columns in a separate list. Finding orphans matters because they clutter the model, slow down maintenance, and can hide real problems (a measure that used to feed a KPI and silently stopped).

One rule drives everythingThe app follows each measure forward through everything that consumes it (other measures, calculated columns, field parameters, calculation groups) and records what it finally reaches: a visual, an active filter, a security role, or nothing. The status is read off that result. The same calculation feeds the sidebar badges, the Dependents grid, the Model Health dashboard, and the toolbar count, so every number in the UI agrees.

The four statuses, from healthiest to most disconnected

In usebadge: none · grid: "in use"

The measure is displayed on at least one visual, either directly or through another measure, a field parameter, or a calculation group that is on a visual. Not an orphan.

Filter / RLS onlybadge: "filter/RLS" · Health: "Filter / Security Orphans"

No visual shows it, but it is actively filtering a visual, page, or report, or it is referenced by a row-level-security rule. It is doing real work that a reader cannot see. Usually keep. Deleting it would change what users are allowed to see.

Visual orphanbadge: "no visual" · Health: "Visual Orphans"

Nothing displays it and no filter or role uses it, but other measures or calculated columns still reference it. It is wired into the model, yet nothing surfaces the result. Investigate. Either the chain above it is also unused, or something was disconnected by mistake.

True orphanbadge: "orphan" · Health: "True Orphans"

Referenced by nothing at all: no visual, no measure, no calculated column, no filter, no security role. Completely disconnected. Safest to delete after checking the limits below.

When this document, the sidebar's "True orphans only" filter, or a colleague says "orphan" without qualification, they mean the last category: a True Orphan. The toolbar's "N orphans" count is the total of the three orphan categories (Filter/RLS, Visual, True); Model Health breaks that total down.

Column (field) orphans: a separate list on purpose

Model Health also lists unused columns, using the strictest rule: nothing references the column at all, no measure, calculated column, visual, active filter, security role, field parameter, or relationship. Relationship key columns are always treated as in use. Columns are listed separately from measures because the concern is different: an unused column costs memory and refresh time, while an unused measure is a maintenance burden. Mixing the two lists makes both harder to act on.

What counts as "used"

  • Placed on a visual. In a chart, card, table, matrix, slicer, KPI, or any other visual's data fields.
  • Used by another measure that is used. If Net Sales = [Total Sales] * 0.9 and Net Sales is on a visual, then Total Sales is in use, even if it never appears on a visual itself. The tool follows these chains to any depth.
  • Inside a field parameter or calculation group that is used. If a visual uses a field parameter (a dropdown that swaps measures), every measure the parameter can select counts as used.
  • Actively filtering. The measure sits in the visual, page, or report filter pane and that filter has a value applied. This counts as Filter/RLS usage, not as "in use", because nothing displays the number.
  • Referenced by a row-level-security role. Same category as filters: real work, invisible to readers.

What does not count

  • On a filter panel with no value set. A field sitting in the filter pane with "(All)" selected is not filtering anything. The report would look identical if it were removed. The app records the reference so it can be listed, but ignores it when grading usage. (The original project counted any filter-pane appearance as usage; this fork changed that.)
  • Referenced only by other orphans. If measure A is used only by measure B, and B reaches nothing, then A is a Visual Orphan and B is a True Orphan.
  • Existing in the model. Being defined is not being used.

How "actively filtering" is decided

Each filter in a PBIP file is a small JSON object. When a user applies a value in Power BI Desktop, the file gains a Where clause describing the condition. The tool checks for that clause at all three scopes (visual, page, report):

Limits to be honest aboutThe tool only sees the PBIP files you load. A measure used by a report that was not loaded, by an Excel "Analyze in Excel" connection, by a paginated report, by a composite model elsewhere, or by an external tool querying the dataset will look like an orphan here. Treat even a True Orphan as "nothing in these files uses this", a prompt to confirm with the report owners, not an automatic delete list.

How the computation works (for the technically curious)

Every "uses" relationship is an edge in the graph, and each edge carries its type (visual binding, measure reference, filter reference with an isActive flag, RLS reference, and so on). classifyMeasureUsage() in packages/core/src/graph/graphBuilder.js walks forward from a measure along consumer edges. Filter and RLS edges are treated as terminal: they set a flag but are not followed further, so a page-level filter can never be mistaken for "displayed on a visual" by walking page → visuals. Reaching a visual node sets in use. Having any model consumer at all (a measure or calculated column) sets the dependent count. The category is then: visual reached → none; else active filter or role reached → filterSecurity; else dependents > 0 → visual; else → true. findColumnOrphans() in the same file implements the column rule, and findOrphansByCategory() in impactAnalysis.js feeds Model Health. The behaviour is pinned by orphanCategories.test.js and filterUsage.test.js.

8. Deeper dive: which files do what

The repository is split into two halves. The engine (packages/core/) knows nothing about browsers; give it file contents, it returns a graph. The web app (src/ and index.html) handles reading folders, drawing, and clicks. The VS Code extension reuses the same engine. This separation is why the engine can be tested with plain unit tests.

Legend: reads files engine / logic user interface

Engine: parsing PBIP files into data

FileRole
packages/core/src/parser/tmdlParser.jsengine Reads TMDL text files (the semantic model). Extracts tables, columns, measures with their DAX, partitions with their Power Query (M) source, relationships, and the data source behind each M query (server, database, schema, table). Also detects column renames inside M so a Power BI column can be traced back to its original source name.
packages/core/src/parser/roleParser.jsengine Reads RLS role files and extracts which measures and columns each security rule's DAX references.

packages/core/src/parser/pbirParser.jsengine Reads PBIR JSON files (the report). Extracts pages, visuals, each visual's bound fields, and filter-pane fields at visual/page/report scope with their active/inactive state. Tags each page and visual with the report it came from.

packages/core/src/parser/projectStructure.jsengine Looks at file paths and sorts them into buckets: table files, role files, relationship files, expression files, visual files, page files.

A note on node IDs (useful when reading the code)

Every object in the graph has a string ID that doubles as documentation: table::Sales, column::Sales.Amount, measure::Sales.Total Sales, visual::<page>/<visualId>. In a multi-report workspace, the semantic model that the most reports share is the "primary" and keeps these plain IDs, so one Total Sales node exists no matter how many reports show it. Visuals and pages carry their report name, and any additional, different semantic model is prefixed so its objects can never collide with the primary model's.

9. Questions a committee is likely to ask

Does it change our Power BI files or data?

No. It opens the folder in read-only mode and never writes to it. It does not connect to any data source; it only reads the text that describes the model. The only files it creates are exports a user explicitly clicks to download.

Where does our data go?

Nowhere. Parsing and drawing happen inside the browser tab. There is no server component. Closing the tab discards everything. The code was checked for network calls: the only one fetches the bundled sample from the app's own host.

Does it need a license or subscription?

No. MIT-licensed open source, free for commercial and internal use. No per-seat cost. The only obligation is to keep the license file with the code.

What do we have to install?

For a user running it locally: Node.js once, then double-click the launcher. For a hosted copy: build once and publish the static dist/ folder to any internal HTTPS web server; users then need only Chrome or Edge.

How confident can we be in its answers?

The engine has 133 automated tests and the logic is readable JavaScript. Its answers are only as complete as the files it is given: it cannot see usage in reports or workbooks that were not loaded. Treat results, especially the orphan lists, as a strong starting point for a human review rather than an automatic action.

What is the difference between the orphan numbers in the toolbar and in Model Health?

The toolbar shows the total of all three orphan categories. Model Health splits that total into True, Visual, and Filter/RLS, and adds a separate list of unused columns. The sidebar's "True orphans only" filter shows just the first category. All come from the same calculation.

What happens if the original author stops maintaining it?

The code is small, dependency-light, and already forked and modified in-house. It can be maintained by any JavaScript developer. Dependency versions are pinned.

Does it work offline?

Yes, once the page is loaded. It needs no internet connection to analyse a project. (This guide loads a font from Google Fonts for its own styling; the app itself ships its own CSS.)

Does the git feature need repository credentials?

No. It reads the .git folder already on disk. It never contacts GitHub, Azure DevOps, or any remote.

10. Glossary

PBIPPower BI Project. The folder-based save format where a report is stored as text files instead of a single .pbix. Enables version control.
.SemanticModelThe folder holding the data model: tables, columns, measures, relationships, security roles, and data source queries. Written in TMDL.
.ReportThe folder holding the report layout: pages, visuals, filters, bookmarks. Written as PBIR JSON. Several reports can point at one semantic model.
Workspace folderThis tool's term for a folder containing several PBIP reports, usually sharing a semantic model, analysed together.
TMDLTabular Model Definition Language. A readable text format for the semantic model (one file per table, one per role).
PBIRPower BI Enhanced Report format. JSON files, one per page and one per visual.
DAXData Analysis Expressions. The formula language for measures and calculated columns, e.g. SUM(Sales[Amount]).
MeasureA named DAX calculation (Total Sales, YoY Growth). Measures can reference other measures, forming chains.
VisualA chart, card, table, slicer, or other element on a report page.
Filter paneThe panel in Power BI where fields can be added to filter a visual, a page, or the whole report. A field can sit there with or without a value applied.
RLS (row-level security)Model rules that restrict which rows each user can see. Written as DAX, so they can reference measures and columns.
Field parameterA model feature that lets a report user switch which measure or column a visual shows from a dropdown.
Calculation groupA model feature that applies a transformation (YTD, prior year, % of total) to any measure.
Power Query / MThe data-loading language. Each table's partition has an M script that connects to a source and may rename columns.
